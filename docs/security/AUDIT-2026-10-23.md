# Security audit: MyFinancialTracker   Date: 2026-10-23   Commit: 1996e36
Scope: whole app (focus: new auth + per-user scoping)   Stack: Bun 1.4.3 `Bun.serve` routes, React 18 client (Bun HTML bundle), Drizzle 0.45 + bun:sqlite, email/password (argon2id) + hashed server-side session cookie
Summary: CRITICAL 0 · HIGH 0 · MEDIUM 3 · LOW 7   Dependencies: `bun audit` → 1 moderate (esbuild, dev-only)

**Overall:** the core holds. I traced every route from request to query: none is reachable without a session except the 3 auth routes and health (`app.ts:302`). Every repository query is scoped through `uid()`, which fails closed (`context.ts:206-210`). Every client-sent foreign key (categoryId, cardId, parentId, moveTo, childrenTo) is looked up through a scoped repository before use. Zod strips unknown keys, so `userId` can't be mass-assigned. There is no SQL injection: all `sql` template values are bound params, and LIKE wildcards are escaped. There is no XSS sink: there's no `dangerouslySetInnerHTML`, and colours are regex- and CHECK-validated and go through React's `style` object. Secrets are clean in the tree and in history. The findings below are about the abuse resistance of the login limiter and about deployment hardening.

## Findings

### SEC-1 · MEDIUM · Anyone can lock a known user out of login indefinitely   Status: open
- Where: `apps/web/src/server/routes/auth.ts:68-70` (limiter `auth.ts:175-184`)
- OWASP/ASVS: A07 / V2.2.1 (anti-automation must not enable account DoS)
- Evidence: `const okEmail = limiter.allow(\`login:email:${email}\`, 8, 15 * MINUTE); if (!okIp || !okEmail) throw tooMany();` The check runs **before** the password is verified, and every attempt counts, including the victim's own.
- Exploit: an attacker who knows the victim's email sends 9 bad logins every 15 minutes, from any IP (the IP limit is 30, so one IP is enough). Every login by the victim, even with the correct password, gets a 429. This is a targeted, indefinite denial of access to their financial data.
- Fix (owner: backend, **decision**): key the strict lockout on `email+ip` (e.g. `login:email:${email}:${ip}`, 8/15 min) and keep a looser per-email cap (e.g. 100/15 min) as the distributed brute-force backstop. That is one changed key plus one extra `allow` line. The architect decides the limits.
- Verify: 9 failed logins for `carol@` from IP A, then a correct login from IP B → 200.

### SEC-2 · MEDIUM · Unbounded limiter map lets one client burn the server's CPU and memory   Status: open
- Where: `apps/web/src/server/routes/auth.ts:68-69`, `apps/web/src/server/auth.ts:176`
- OWASP/ASVS: A04 / V11.1.4
- Evidence: login calls `allow()` for the IP **and** for the email before testing either. An IP that is already over its limit still inserts a new `login:email:<x>` entry for each new email. Once the map passes 10,000 entries, **every** `allow()` walks the whole map (`for (const [k, v] of hits)`), and entries live 15 minutes.
- Exploit: one unauthenticated client posts `{"email":"<random>@x.io","password":"x"}` in a loop. These requests are cheap (429 before argon2), but the map grows by one entry per request. Each request, including legitimate logins, then pays an O(n) sweep on the single JS thread. With a few hundred thousand entries the server stalls.
- Fix (owner: backend): check the IP first and return early, as register already does (`auth.ts:50`): `if (!limiter.allow(ip…)) throw tooMany();` then the email `allow`. Also make the sweep bounded: run it at most once per window, or clear the map when it is still over the cap after sweeping. Mark it with a `ponytail:` comment.
- Verify: 1,000 logins from one IP with distinct emails → map size ≤ 31.

### SEC-3 · MEDIUM · Register reveals whether an email has an account (409)   Status: open (dev deferral)
- Where: `apps/web/src/server/routes/auth.ts:55-57`
- OWASP/ASVS: A07 / V2.2 (account enumeration)
- Evidence: an existing email → 409 "Couldn't create an account with that email…"; a new email → 201. Login is careful to avoid enumeration (dummy hash, same message), but register undoes that.
- Exploit: an attacker checks a list of emails for membership in a finance app (phishing targeting, and it confirms targets for SEC-1). The speed is capped at 10/h per IP and 5/h per email, but it scales with IPs.
- Fix (owner: backend, **decision**): either (a) accept it with the current rate limits and document it, which is common for apps without email delivery, or (b) when email verification exists, always answer "Check your inbox" and send "you already have an account" mail. Option (b) needs an email service, so the architect decides.
- Verify: (b) register with an existing email and with a new one → same status and body.

### SEC-4 · LOW · HTML document and static assets carry no security headers (no frame protection)   Status: open (dev deferral)
- Where: `apps/web/src/server/index.ts:327` (`"/*": index`), `apps/web/src/client/index.html:12-15`. Live probe: `GET /` and `/_bun/asset/*.css` return only Content-Type, ETag and Date.
- OWASP/ASVS: A05 / V14.4.3, V14.4.4, V14.4.5
- Evidence: there is no `frame-ancestors`/`X-Frame-Options`, no `nosniff` and no `Strict-Transport-Security` on the page and the bundle. A meta CSP can't express `frame-ancestors`.
- Exploit: clickjacking by framing the app. This is **mitigated by `SameSite=Lax`**: a cross-site iframe doesn't receive the session cookie, so the framed app is signed out. A same-site attacker (a sibling subdomain on a shared parent domain) is not blocked. HSTS is missing, so first-visit SSL stripping is possible in production.
- Fix (owner: backend): at the production reverse proxy, add `Content-Security-Policy: frame-ancestors 'none'`, `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff` and `Strict-Transport-Security: max-age=31536000` on all non-API responses. Write it down in the deploy README. No code change is needed.
- Verify: `curl -sI https://<prod>/` shows all four headers.

### SEC-5 · LOW · The limiter collapses behind a proxy and resets on restart   Status: open (dev deferral)
- Where: `apps/web/src/server/routes/auth.ts:29` (`server.requestIP(req)`), `apps/web/src/server/auth.ts:171`
- OWASP/ASVS: A04 / V11.1
- Evidence: behind a reverse proxy, `requestIP` is the proxy's address, so every user shares one bucket of 30 logins per 15 min and 10 registers per hour. The map is per-process and is cleared on every restart or deploy.
- Exploit: once deployed behind a proxy, one actor spends the shared IP budget and blocks login for everyone. A restart also resets brute-force counters. This is acceptable for a single local process, which is today's deployment.
- Fix (owner: backend, **decision**): when a proxy is introduced, read the client IP from the proxy's header **only** when the request came from the trusted proxy address. Move the counters to a SQLite table if there's more than one instance.
- Verify: behind the proxy, 31 bad logins from client A don't affect client B.

### SEC-6 · LOW · Sessions have no absolute lifetime, and expired rows are never purged   Status: open (dev deferral)
- Where: `apps/web/src/server/auth.ts:142-145` (sliding renewal), `auth.ts:160` (`purgeExpired`, which has no caller)
- OWASP/ASVS: A07 / V3.3.2 (absolute timeout), V3.3.1
- Evidence: each use pushes `expiresAt` 30 days forward with no cap, so a stolen cookie stays valid as long as it's used monthly. Expired rows are deleted only when presented (`auth.ts:137-139`).
- Exploit: a leaked cookie (from a shared device or a backup) gives open-ended access until a password change. The DB accumulates dead token hashes, which isn't exploitable since they're hashed and rejected.
- Fix (owner: backend, **decision** on the cap, e.g. 90 days): use the existing `created_at`: `if (row.createdAt.getTime() + MAX_AGE <= now) → delete, return null`. Call `auth.purgeExpired()` once at startup in `index.ts` and then from a `setInterval(…, DAY)`.
- Verify: a session with `created_at` older than the cap → 401 even though `expires_at` is in the future.

### SEC-7 · LOW · No request body size limit (Bun default 128 MB) on unauthenticated routes   Status: open
- Where: `apps/web/src/server/index.ts:322-330` (no `maxRequestBodySize`), `apps/web/src/server/http.ts:361` (`req.json()`)
- OWASP/ASVS: A04 / V13.1.3
- Evidence: a 3 MB login body was fully read and parsed before Zod rejected it (probe → 400).
- Exploit: parallel large POSTs to `/api/auth/login` or `/register` push memory toward 128 MB per request without a session.
- Fix (owner: backend): add `maxRequestBodySize: 64 * 1024` to `Bun.serve` (the largest legitimate body is under 2 KB).
- Verify: a 100 KB POST → 413.

### SEC-8 · LOW · Auth events are not logged   Status: open
- Where: `apps/web/src/server/routes/auth.ts:49-113` (no log on register, login success/failure, 429, logout or password change)
- OWASP/ASVS: A09 / V7.1.3
- Evidence: the only server log is `console.error(err)` for 500s (`http.ts:391`).
- Exploit: credential stuffing, SEC-1 lockouts and session theft leave no trace to investigate.
- Fix (owner: backend): one `console.info(JSON.stringify({ evt, userId, ip, ok }))` per auth outcome. Never log the email+password pair, tokens or hashes.
- Verify: a failed login produces one log line without the password.

### SEC-9 · LOW · Session cookie lacks the `__Host-` prefix   Status: open
- Where: `apps/web/src/server/auth.ts:15`, `auth.ts:85-96`
- OWASP/ASVS: A07 / V3.4.4
- Evidence: the cookie is `mft_session=…; Path=/; HttpOnly; SameSite=Lax; Secure`, with no prefix.
- Exploit: a sibling subdomain or a network attacker on plain HTTP can plant a `mft_session` cookie (session fixation/tossing). Login rotates the token, which limits the impact.
- Fix (owner: backend): in production, name it `__Host-mft_session` (it already has Secure, Path=/ and no Domain). Keep the plain name on http localhost, where `Secure` is off.
- Verify: production `Set-Cookie` starts with `__Host-`.

### SEC-10 · LOW · Vulnerable esbuild 0.18.20 in the dev toolchain   Status: open
- Where: `bun.lock:155` (`drizzle-kit > @esbuild-kit/core-utils > esbuild@0.18.20`)
- OWASP/ASVS: A06
- Evidence: `bun audit` reports GHSA-67mh-4wv8-2f99 (moderate: the esbuild dev server answers cross-origin requests).
- Exploit: none in this app. drizzle-kit doesn't start esbuild's serve mode, and the package isn't in the production server. Ranked LOW because it's dev-only and not reachable.
- Fix (owner: backend): re-run `bun audit` after drizzle-kit upgrades. Optionally add `"overrides": { "esbuild": "^0.25.0" }` in the root `package.json`, then confirm that `db:generate` still works.
- Verify: `bun audit` → 0 advisories.

## Hardening notes
- `nextPath()` (`client/lib/session.ts:88`) accepts `/\evil.com`, which browsers normalise to `//evil.com`. Today `history.replaceState` throws on cross-origin URLs, so there's no open redirect, but also reject `\`: `!/^\/[\/\\]/.test(next)`.
- `console.error(err)` (`http.ts:391`) can print Drizzle errors that include query params (token hashes, password hashes on the insert path). Log `err.message` plus the route instead of the raw object.
- The DB doesn't enforce same-user foreign keys (a transaction's card/category, a category's parent). The app checks them through scoped lookups. Add isolation tests for the untested paths: B `PATCH /api/categories/<B id>` with `parentId: <A id>` → 400; B `DELETE /api/categories/<B id>?moveTo=<A id>` → 400; B `POST /api/cards/<B card>/installments` with A's `categoryId` → 400.
- Password policy is 8 characters minimum plus a 35-word blocklist. ASVS recommends 12 or a larger breached-password list (offline). This is a product decision.
- `development` mode (`index.ts:329`) is on unless `NODE_ENV=production`. `bun run start` sets it, but running `bun src/server/index.ts` directly on a server would enable HMR and Bun's error overlay. Consider `development: process.env.NODE_ENV === "development"`.
- Behind a TLS-terminating proxy, `new URL(req.url).origin` (`security.ts:251`) may be `http://…` while the browser sends `https://…`. All writes would then be refused (fails closed, but plan for it). `isSecure()` (`auth.ts:80`) would drop `Secure` if the proxy rewrites Host to localhost.
- `seed-demo.ts` writes demo data into an existing `demo@mft.local` account. If a stranger registered that email on a live server first, running the seed there would hand them the demo data. Never run seeds in production.
- localStorage holds only UI state (alert dismissals by card id, open categories). It isn't per user and isn't cleared on sign-out, which is minor on shared devices.

## Not checked
- File upload, CSV/Excel export, password reset, email verification and CORS: none exist in the app.
- Runtime tests (`bun test`) were not run: running project scripts isn't allowed. Isolation was verified by code trace plus a read of `isolation.test.ts`, which covers 15 cross-user routes.
- A live two-user IDOR probe was not sent: it would have created accounts on the running dev DB. Live probes covered only headers, the 401 gate, CSRF 403/415, unknown methods, static file exposure (`/data/mft.sqlite` → SPA HTML, not the DB) and body size.
- The production build output and proxy config don't exist yet.
